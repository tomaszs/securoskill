# Multi-tenancy and SaaS isolation

## When to use

Load this skill when work touches **multi-tenancy and saas isolation**: design, implementation, code review, or incident follow-up.

## Workflow

1. Skim sub-areas in [reference.md](reference.md) and pick those that match the change.
2. Apply rules from **policy → design → implementation → verification → operations** for each matching sub-area.
3. For SQL injection, XSS, SSRF, authz, secrets, or other classics, use the dedicated sub-section rather than generic advice.
4. Record gaps as security requirements or tests before merge.

## Sub-areas covered

- **Tenant identification**: Subdomain routing, Header spoofing, JWT tenant claim, …
- **Data isolation models**: Separate DB, Shared schema RLS, Shard keys, …
- **Tenant-scoped authorization**: Admin impersonation, Support access, API keys per tenant, …
- **Billing and plan enforcement**: Feature flags per plan, Usage metering, Trial abuse, …
- **Custom domains and TLS**: Domain verification, Cert provisioning, Host header attacks, …
- **Tenant export and backup**: Bulk export IDOR, Scheduled exports, Restore to wrong tenant, …
- **Per-tenant integrations**: OAuth app installs, Webhook endpoints, SCIM provisioning, …
- **Noisy neighbor and quotas**: CPU limits, Queue fairness, DB connection pools, …
- **Tenant onboarding**: Self-signup abuse, Email domain verification, Invite flows, …
- **Tenant offboarding**: Data deletion, Legal hold, Reactivation, …
- **Compliance per tenant**: Data residency, Audit logs per tenant, DPA variants, …
- **SaaS penetration patterns**: Horizontal privilege, Vertical to platform admin, Cross-tenant file access, …
