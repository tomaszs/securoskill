# Human factors, social engineering, and support abuse

## When to use

Load this skill when work touches **human factors, social engineering, and support abuse**: design, implementation, code review, or incident follow-up.

## Workflow

1. Skim sub-areas in [rules.md](rules.md) and pick those that match the change.
2. Apply rules from **policy → design → implementation → verification → operations** for each matching sub-area.
3. For SQL injection, XSS, SSRF, authz, secrets, or other classics, use the dedicated sub-section rather than generic advice.
4. Record gaps as security requirements or tests before merge.

## Sub-areas covered

- **Developer phishing**: Fake npm, Malicious PR, Stolen OAuth, …
- **Customer support takeover**: Security questions, SIM swap, Email change, …
- **Vishing and impersonation**: CEO fraud, Vendor impersonation, Callback phishing, …
- **Insider threat**: Offboarding gaps, Privileged monitoring, Data exfil jobs, …
- **Physical access to dev assets**: Unattended laptops, USB drops, Office tailgating, …
- **Security awareness**: Phishing sims, Report buttons, Metrics, …
- **Incident communications**: Status page accuracy, Rumor control, Legal hold comms, …
- **Bug bounty operations**: Researcher relations, Safe harbor, Duplicate handling, …
- **Law enforcement requests**: Subpoena validation, Emergency disclosure, Transparency reports, …
- **Social engineering of login flows**: Fake OAuth apps, Consent screen tricks, Passwordless confusion, …
- **Documentation and wiki leaks**: Public Confluence, Pastebin creds, Runbooks with secrets, …
- **BPO and outsourced access**: VPN accounts, Time-bound access, Screen monitoring, …
